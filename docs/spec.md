# Спека: приложение-симулятор бизнес-воркшопов

Версия 1. Основа — воркшоп «Малыш и лимонад», контекст в `context-v16.md`.
Соло-режим подробно — в `solo-mode.md`.
Строит: Evgenii с Claude Code. Аудитория: внутреннее обучение в банке и
консалтинговые клиенты.

---

## 1. Зачем

Воркшоп сейчас держится на связке «дека + таблица команды + таблица ведущего +
десять Google Форм». Это даёт двойной ввод, ручную транскрипцию чисел с экрана,
хрупкую склейку ответов и жёстко зашитый сценарий. Приложение заменяет всё это
одним источником правды: движок считает, команды вводят только решения, ведущий
видит всё сразу.

Вторая цель — сценарий перестаёт быть жёстким. Ветки от решений, случайные
события, подключаемые модули (например, экономика маркетплейса) и конфиг прогона,
который генерирует ИИ под конкретную задачу.

---

## 2. Режимы и каналы

**С тренером.** Синхронный: все команды на одном шаге, тренер переключает.
Команды вводят решения, тренер закрывает приём, движок показывает факты дня.
У тренера отдельный экран: ходы всех команд, таблица вариантов, деньги команд.
Замена текущей таблицы ведущего.

**Самостоятельно.** Один игрок, свой темп. Тот же движок, но вместо тренера —
встроенные пояснения после каждого факта и вопросы для рефлексии вместо ретро.
Допущение: соло-режим — одиночный игрок, не команда онлайн. Подтвердить.

**Каналы.** Веб и Telegram Mini App — одна кодовая база. Mini App это та же
веб-страница внутри Telegram, отличаются только вход и авторизация.

## 3. Архитектура

```
┌──────────────────────────────────────────────────────────┐
│  Сценарий (.md с json-блоками)  →  компилятор  →  JSON   │
└──────────────────────────────┬───────────────────────────┘
                               │
            ┌──────────────────┴──────────────────┐
            ▼                                     ▼
   ┌─────────────────┐                  ┌──────────────────┐
   │   Валидатор     │                  │  Рантайм сессий  │
   │ (все ветки ×    │                  │ (тренер / соло,  │
   │  все события)   │                  │  веб / Telegram) │
   └────────┬────────┘                  └────────┬─────────┘
            │                                    │
            └──────────────┬─────────────────────┘
                           ▼
                ┌─────────────────────┐
                │   Движок симуляции  │
                │ (чистые функции,    │
                │  детерминированный) │
                └──────────┬──────────┘
                           ▼
                ┌─────────────────────┐
                │ Библиотека механик  │
                │ + учётное ядро      │
                └─────────────────────┘
```

Движок — отдельный TypeScript-пакет без зависимостей от UI и базы. Один и тот же
код работает в браузере, на сервере и в CLI валидатора. Это главное требование:
валидатор должен проверять ровно ту логику, которую потом увидят игроки.

**Детерминизм.** Вход движка: сценарий, конфиг, seed, список решений. Выход:
полное состояние на каждом шаге. Одинаковый вход — одинаковый выход, всегда.
Никакого `Math.random()` и текущего времени внутри движка.

## 4. Учётное ядро

Каждая механика не пишет в отчёты напрямую, а порождает **проводки**:
`{ account, amount, node, source }`. P&L, Cash Flow и Баланс — проекции над
журналом проводок.

Смысл: сходимость трёх отчётов гарантируется построением. В таблицах мы
проверяли её руками строкой «должен быть ноль» — здесь это инвариант движка,
который падает в тестах, если нарушен.

Счета v1:

| Счёт | Тип |
|---|---|
| `cash` | актив |
| `receivables` | актив |
| `inventory` | актив |
| `equipment` | актив |
| `loan` | обязательство |
| `retained_earnings` | капитал |
| `revenue` | P&L |
| `cogs` | P&L |
| `waste` | P&L |
| `bad_debt` | P&L |
| `fixed_costs` | P&L |
| `marketing` | P&L |

Проекции:

- **P&L** — обороты по P&L-счетам за период
- **Cash Flow** — обороты по `cash` с разбивкой по `source`
- **Баланс** — остатки активов = обязательства + капитал + текущая прибыль

## 5. Библиотека механик

Экономика в сценарии не пишется формулами. Сценарий выбирает механики из
библиотеки и задаёт им параметры. Это делает генерацию ИИ надёжной (он заполняет
параметры, а не изобретает математику) и валидацию возможной (у каждой механики
известное поведение).

Каждая механика — типизированный компонент:

```ts
interface Mechanic<P, I> {
  id: string;
  paramsSchema: JSONSchema;          // что задаёт сценарий
  inputsSchema?: JSONSchema;         // что вводит игрок на шаге
  step(ctx: StepContext, params: P, inputs: I): StepResult;
}

interface StepResult {
  entries: JournalEntry[];           // проводки
  metrics: Record<string, number>;   // трафик, конверсия, продано...
  stateDelta: Partial<SimState>;     // например, новая когорта долгов
}
```

### Механики v1 — всё, что нужно лимонаду

| Механика | Что делает | Где в лимонаде |
|---|---|---|
| `funnel` | трафик по типу дня × конверсия → спрос | все торговые дни |
| `price_response` | конверсия как функция цены, задаётся таблицей | Д9, Д12 |
| `channel` | стоимость по тиражу, прирост трафика, прирост конверсии при совпадении предложения | Д10, Д13 |
| `batch_production` | объём фиксируется до спроса, непроданное в `waste` | Д1–Д3, Д15 |
| `on_demand_production` | себестоимость на проданное, списаний нет | Д4–Д5, Д12–Д14, Д16 |
| `credit_sales` | доля продаж в долг, когорты с разной возвратностью, день инкассации | Д2–Д3 |
| `fixed_costs` | расход в день, разный для торгового и неторгового дня | парк |
| `capex` | разовая покупка актива | кувшин, оборудование |
| `financing` | приток денег с обязательством | заём папы |
| `inventory` | запас на полке, пополнение по мере продаж, возврат по закупке | кола |

Таблицы, а не формулы эластичности — сознательно. Таблицу видно на экране
тренера, её легко проверить глазами, и она точно воспроизводит числа v16.

### Механики v2 — пример модуля «Маркетплейс»

| Механика | Что делает |
|---|---|
| `take_rate` | выручка площадки = GMV × комиссия, GMV не выручка |
| `two_sided_acquisition` | CAC продавцов и покупателей раздельно |
| `liquidity` | конверсия покупателей зависит от числа продавцов |

Детали модуля — отдельная спека, когда до него дойдёт. Здесь он нужен как
проверка, что архитектура не завязана на лимонад.

## 6. Формат сценария

### Авторский формат — Markdown

Один файл. Фронтматтер YAML — метаданные. Каждый шаг — заголовок уровня 2,
текст слайда в Markdown, модель шага в fenced-блоке `json scenario`.

````markdown
---
id: lemonade
version: 16
title: Малыш и лимонад
locale: ru
duration_min: 90
---

## d2 · Вторник · Двор

Малыш разрешает платить завтра — и во двор приходят даже те, у кого денег нет.
У соседки есть второй кувшин за 15 монет.

```json scenario
{
  "day_type": "yard_weekday",
  "inputs": [
    { "id": "jug", "type": "choice", "options": [0, 15],
      "label": "Покупаем второй кувшин?" }
  ],
  "mechanics": [
    { "use": "capex", "params": { "amount": "$input.jug" } },
    { "use": "credit_sales", "params": {
        "traffic": 35,
        "capacity": { "if": [{"==": [{"var":"input.jug"}, 15]}, 30, 15] },
        "queue": "shared",
        "cohorts": [
          { "id": "would_come_anyway", "size": 6,  "return_rate": 0.667 },
          { "id": "attracted_by_credit", "size": 10, "return_rate": 0.30 }
        ],
        "collect_on": "d3"
    }}
  ],
  "next": "d3"
}
```
````

### Канонический формат — JSON

Компилятор собирает Markdown в один JSON, валидируемый JSON Schema. Рантайм и
валидатор работают только с каноническим JSON. ИИ генерирует сразу канонический
JSON — со схемой он справляется надёжнее, чем с разметкой.

### Язык условий

Условия переходов, параметры, зависящие от решений, и инварианты пишутся на
**JSONLogic**. Безопасен (не исполняет код), сериализуем, ИИ его знает.

## 7. Граф сценария

Сценарий — граф шагов, а не линейка.

```json
"next": [
  { "if": { "==": [{ "var": "state.path" }, "park"] },        "to": "d7_park" },
  { "if": { "==": [{ "var": "state.path" }, "marketplace"] }, "to": "d7_mp" }
]
```

Три вида вариативности:

**Ветки от решений.** Переход зависит от ввода игрока или состояния. Сюжетный
текст шага тоже может ветвиться: `narrative` бывает массивом с условиями.

**Модули.** Подграф, подключаемый к точке входа. Модуль «Маркетплейс» вешается на
Д6 вместо парка. Какие модули активны — решает конфиг прогона.

**Случайные события.** Описаны отдельно, встраиваются в шаги по условию и
вероятности:

```json
{
  "id": "rain",
  "when": { "nodes": ["d12","d13","d14"], "probability": 0.25 },
  "effects": [{ "metric": "traffic", "multiply": 0.5 }],
  "narrative": "С утра дождь. В парке почти пусто."
}
```

### Справедливость в режиме тренера

Один seed на сессию, а не на команду. Все команды получают одинаковые события —
иначе разбор «почему у вас разные деньги» теряет смысл: разница должна быть от
решений, а не от удачи.

В соло-режиме seed на каждый прогон — это и даёт реиграбельность.

## 8. Уроки и инварианты

Главная часть спеки. Каждый учебный вывод описан как набор проверяемых условий.

Два вида инвариантов:

**Путевые** — выполняются на любом пути по графу.

```json
{ "id": "balance_closes",
  "assert": { "==": [{ "var": "report.balance_check" }, 0] } }
```

**Контрастные** — сравнивают два пути, различающихся одним решением. Именно они
доказывают уроки.

```json
{
  "lesson": "revenue_is_not_cash",
  "title": "Считать продажу деньгами",
  "contrast": { "node": "d2", "input": "jug", "a": 15, "b": 0 },
  "assert": { "and": [
    { ">": [{ "var": "a.pl.cumulative@d3" },   { "var": "b.pl.cumulative@d3" }] },
    { "<": [{ "var": "a.cash@d3" },            { "var": "b.cash@d3" }] }
  ]}
}
```

Читается так: у купивших кувшин прибыль к Д3 выше, а денег меньше. Если
генерация ИИ даст возвратность 55%, второе условие упадёт, и сценарий не будет
принят.

Уроки лимонада, которые должны быть инвариантами v1:

| Урок | Проверка |
|---|---|
| Продажа ≠ деньги | Д2: кувшин → прибыль выше, Cash ниже |
| Скидка без расчёта | Д5: продажи выше, прибыль ниже, трафик тот же |
| Юнит-экономика ≠ бизнес | Д8: маржа с продажи > 0, прибыль дня < 0 |
| Цена: покупатели и деньги — разные максимумы | Д12: максимум продаж и максимум прибыли при разных ценах |
| Канал зависит от предложения | Д10 все тиражи хуже нуля; Д13 лучший тираж лучше нуля |
| Контекст дня, а не бизнес | Д15: конверсия ±1 п.п. к Д14, трафик ниже вдвое |
| Прогноз по базе | Д16: прогноз по воскресенью < по неделе < по понедельнику |

### Бюджет времени

У каждого шага оценка длительности. Инвариант: на любом пути сумма ≤
`duration_min` сценария. Иначе ветка, которая выглядит безобидно, ломает
90-минутный слот.

## 9. Валидатор

CLI и функция движка: `sim validate scenario.md`.

1. Компилирует сценарий, проверяет JSON Schema
2. Перебирает пути: все комбинации решений × все исходы событий. Для больших
   графов — сэмплирование с покрытием каждого ребра хотя бы раз
3. На каждом пути проверяет путевые инварианты
4. Для каждого контрастного инварианта строит пары путей и проверяет
5. Проверяет бюджет времени

Отчёт: какой урок, на каком пути, какое условие, какие числа. Формат пригоден
для обратной подачи в ИИ — это основа цикла генерации (п. 11).

### Золотой тест

Сценарий лимонада из v16, референсный путь (кувшин куплен, кола 7, 300 флаеров,
лимонад 9, 300 флаеров, заготовка 19) обязан воспроизвести:

| Показатель | Значение |
|---|---:|
| Прибыль Сезона 1 | 203 |
| Cash конец Сезона 1 | 188 |
| Прибыль Сезона 2 | 418 |
| Cash конец игры | 776 |
| Накопленная прибыль | 621 |
| Проверка баланса | 0 |

Плюс все значения таблиц вариантов из `context-v16.md`, раздел 3. Это регрессия на каждое
изменение движка.

## 10. Рантайм сессий

### Режим с тренером

1. Тренер выбирает сценарий и конфиг, создаёт сессию
2. Получает ссылку и QR — веб и Telegram deep link
3. Команды заходят по коду, выбирают имя, без регистрации
4. Тренер открывает шаг → команды видят текст и поля ввода
5. Команды отправляют решение, тренер видит, кто отправил
6. Тренер закрывает приём → движок считает → все видят факты дня
7. Тренер переходит к следующему шагу

Повторная отправка до закрытия приёма перезаписывает решение. После закрытия —
нет. Тренер может продлить приём.

**Экран тренера:** ходы всех команд на текущем шаге, таблица всех вариантов с
результатами, деньги команд. Это прямая замена вкладок дня и блока «Деньги
команд» из таблицы ведущего.

**Экран команды:** текст шага, поле решения, после раскрытия — воронка,
экономика дня, Cash. P&L, Cash Flow и Баланс — в конце сезона.

### «Посчитай сам»

В таблицах команда сама превращала продажи в деньги — это часть урока. В
приложении считает движок, но шаг может требовать расчёт до раскрытия:

```json
{ "id": "breakeven", "type": "quiz", "answer": 35,
  "label": "Сколько бутылок нужно, чтобы выйти в ноль?" }
```

Так сохраняется Д8: команда считает, потом видит правильный ответ.

### Соло-режим

Описан отдельно в `solo-mode.md`.

## 11. ИИ-генерация конфигов

### v1 — отдельно от приложения

Генерация в Claude, результат загружается файлом. В репозитории лежит
**пакет генерации**:

- JSON Schema канонического сценария
- описание библиотеки механик — что делает каждая, какие параметры
- инструкция: как описывать уроки как инварианты
- пример — сценарий лимонада целиком

Цикл: запрос («экономика маркетплейса для PO банка, 60 минут, 8 команд») →
ИИ генерирует JSON → `sim validate` → при ошибках отчёт валидатора подаётся
обратно → повтор до чистого прогона.

### v2 — внутри приложения

Тот же цикл, но тренер пишет запрос в интерфейсе. Валидатор уже есть, меняется
только место вызова модели. Строить после того, как v1 прошёл несколько реальных
генераций.

## 12. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык | TypeScript везде | движок общий для клиента, сервера и CLI |
| Фронт и бэк | Next.js, App Router | один проект, деплой на Vercel |
| Хостинг | Vercel | облако разрешено |
| База | Postgres (Neon через Vercel) + Drizzle | сессии, команды, решения |
| Синхронизация | опрос раз в 2 секунды | для v1 достаточно; realtime-сервис — если не хватит |
| Telegram | Mini App SDK, проверка `initData` на сервере | вход без пароля |
| Схемы | JSON Schema + Ajv | валидация сценариев |
| Условия | json-logic-js | безопасные выражения |
| Тесты | Vitest | золотой тест и инварианты |

Про синхронизацию: опрос проще в отладке и в Telegram работает без сюрпризов.
Задержка две секунды на воркшопе незаметна.

**Хранится в базе:** сессия, её сценарий и seed, команды, решения по шагам.
Состояние не хранится — пересчитывается движком из решений. Детерминизм делает
это дешёвым и исключает рассинхрон.

## 13. Этапы

| Этап | Содержание | Готово, когда |
|---|---|---|
| M0 | Движок, учётное ядро, механики v1, компилятор, валидатор, сценарий лимонада | золотой тест и все инварианты зелёные в CLI |
| M1 | Режим с тренером, веб | проведён тестовый воркшоп на лимонаде |
| M2 | Соло-режим и Telegram Mini App | один игрок проходит лимонад в Telegram |
| M3 | Случайные события и сюжетные ветки | валидатор проходит сценарий с событиями |
| M4 | Второй модуль — маркетплейс | второй сценарий без правок движка |
| M5 | ИИ-генерация внутри приложения | тренер генерирует и запускает сценарий |

M0 без интерфейса сознательно. Если движок и валидатор не воспроизводят v16 из
CLI, всё остальное строится на песке.

M4 — проверка архитектуры. Если для маркетплейса придётся править движок, а не
только добавлять механики, значит граница проведена неверно.

## 14. Открытые вопросы

Не решены, решать по мере дохождения:

- Консалтинговый контур: у клиентов свой брендинг? Разделение данных между
  организациями нужно с M1 или позже?
- Хранение результатов: сколько держать, нужна ли выгрузка для отчёта клиенту?
- Языки: только русский или сразу русский и таджикский/английский?
