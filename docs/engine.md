# Движок

Версия 1. Часть платформы MiL ([spec.md](spec.md), п. 0).

Движок исполняет сценарий: по ходам команд считает каждый шаг, ведёт учёт
и проверяет сценарии перед тем, как они попадут в приложение. Он ничего не
знает об экранах, сессиях и базе, а приложение не знает экономики: оно
показывает снимки, которые вернул движок.

Связанные документы: [mechanics.md](mechanics.md) — библиотека механик,
[scenario-format.md](scenario-format.md) — формат сценария.

---

## 1. Граница: движок и сценарий

| | Движок (код) | Сценарий (`.md`) |
|---|---|---|
| Что | как считать | что считать |
| Содержит | учётное ядро, механики, порядок исполнения шага, компилятор, проверку | шаги, легенды, числа, ходы, раскладку результатов, выводы, эталонные проверки |
| Меняется | редко, с тестами и развёртыванием кода | для каждого воркшопа, только `.md` |
| Знает о другой стороне | формат сценария и контракт механик | имена механик и их параметры |

| Задача | Что правится | Код |
|---|---|---|
| Новый воркшоп из существующих механик | новый каталог в `scenarios/` | ничего |
| Изменить числа, тексты, ходы, длительности | `.md` сценария | ничего |
| Другое число фаз и шагов, свой состав слайдов результатов | `.md` сценария | ничего |
| Новый учебный вывод с проверкой | `.md`, раздел `# lessons` | ничего |
| Новая экономическая механика | компонент в библиотеке механик + описание + тесты | ни приложение, ни учётное ядро |
| Новый тип панели на слайде или поля хода | приложение: каталог панелей | ни движок, ни сценарии |
| Новый тип счёта или отчёта | учётное ядро | — |

Первые четыре строки — повседневная работа: новое развёртывание с новым
`.md`, без изменения кода. Пятая — расширение библиотеки механик. Две
последние — изменения платформы: если они понадобились, это повод
пересмотреть каталог, а не завести особый случай под один сценарий.

Движок:

- не исполняет код из сценария: условия и формулы в сценарии — JSONLogic,
  безопасный язык без доступа к чему-либо кроме переменных снимка;
- не вызывает ИИ;
- не имеет особых случаев «если сценарий такой-то».

Как это проверяется:

- **тест «без знания сценариев»** — CI собирает идентификаторы шагов,
  параметров и ходов всех `scenarios/*` и ищет их в исходниках движка и
  приложения. Совпадение — ошибка;
- **два сценария с разной структурой** с первого этапа, любое изменение
  кода должно оставить зелёными оба;
- **граница пакетов** — движок не импортирует UI и базу, приложение не
  импортирует механики, а читает только снимки.

## 2. Вход и выход

```ts
runSession(scenario, teams: TeamDecisions[]) → TeamSnapshots[]
runPath(scenario, decisions) → Snapshot[]      // один путь: одна команда
```

Вход — скомпилированный сценарий и ходы. Выход — снимок на каждом шаге
([scenario-format.md](scenario-format.md), п. 6.3). Одинаковый вход —
одинаковый выход, всегда: никакого `Math.random()` и текущего времени.

На `runPath` построено всё: результаты команд, таблицы вариантов на слайдах,
проверка сценариев. Пересчёт десятка шагов стоит миллисекунды, поэтому
результаты нигде не хранятся — только ходы.

Движок — отдельный TypeScript-пакет без зависимостей. Один и тот же код
работает на сервере приложения, при сборке и в CLI, поэтому проверка
сценария проверяет ровно ту логику, которую потом увидят команды.

## 3. Учётное ядро

Механики не пишут в отчёты. Они порождают сбалансированные транзакции
`{ source, legs: [{account, amount}] }`, сумма ног равна нулю. P&L, Cash
Flow и Баланс — проекции над журналом. Поэтому сходимость трёх отчётов
гарантирована построением, а не проверяется строкой «должен быть ноль».

**Знак суммы в журнале: дебет «+», кредит «−».** Активы и расходы растут с
«+», обязательства, капитал и доходы — с «−». Примеры:

| Операция | Ноги транзакции |
|---|---|
| заём 500 | `cash +500, loan −500` |
| продажа за деньги на 70 | `cash +70, revenue −70` |
| продажа в долг на 80 | `receivables +80, revenue −80` |
| ингредиенты на 30 | `cogs +28, waste +2, cash −30` |

В журнале долг 500 хранится как `−500`. Наружу знак журнала не выходит:
снимок шага и отчёты показывают все остатки в естественном знаке
(`balance.loan = 500`), а прибыль — как доходы минус расходы.

### 3.1 План счетов

| Счёт | Тип |
|---|---|
| `cash`, `receivables`, `inventory`, `equipment` | актив |
| `loan` | обязательство |
| `retained_earnings` | капитал |
| `revenue` | доход |
| `cogs`, `waste`, `bad_debt`, `fixed_costs`, `marketing` | расход |

Сценарий может переименовать счёт для слайдов (`accounts` в корневом
блоке). Свои счета — позже.

### 3.2 Проекции

- **P&L** — обороты доходов и расходов за период: шаг, фаза, игра
- **Cash Flow** — обороты по `cash` с разбивкой по `source`. Категорию
  (операционная, инвестиционная, финансовая) задаёт механика, подпись —
  сценарий
- **Баланс** — остатки на конец периода: активы = обязательства + капитал
  + накопленная прибыль

### 3.3 Инварианты

Проверяются на каждом шаге любого сценария, сценарий их не объявляет:

- каждая транзакция сбалансирована;
- `check.balance = 0`;
- все суммы целые;
- `cash` в снимке совпадает с остатком счёта `cash`.

## 4. Исполнение шага

1. `scheduled` — движок исполняет отложенные операции, срок которых
   настал: возврат долгов
2. `finance`, `demand` — механики; затем движок фиксирует спрос
3. `supply` — механика сбыта возвращает `allocation`: сколько единиц
   получил каждый сегмент очереди, плюс свои проводки себестоимости
4. `settle` — движок проводит выручку по сегментам и ставит в расписание
   возврат долгов для сегментов в долг
5. `costs`, `analysis` — механики
6. Снимок шага

Подробно — [mechanics.md](mechanics.md), п. 2–3. Выручку и расписание
ведёт движок, а не механики, поэтому одна механика никогда не вызывается
на шаге дважды и не знает о существовании другой.

Ходы шага доступны его механикам: результаты считаются после закрытия
приёма. Ходы, которые должны повлиять только на следующий день (заказ на
завтра), — это отдельный шаг-ход без механик, на который ссылаются
механики следующего шага.

Граф первой версии линейный: шаги идут в порядке файла сценария.

## 5. Компилятор

Два входа, одна структура внутри:

- `scenario.md` — построчный разбор: важны только заголовки-директивы и
  блоки `sim`, остальной Markdown остаётся текстом для экранов;
- `scenario.json` — та же структура сразу ([scenario-format.md](scenario-format.md), п. 13).

Оба читаются YAML-парсером с позициями узлов (JSON — подмножество YAML).
Каждый узел помнит файл, строку и столбец, поэтому любая ошибка — и
компиляции, и проверки — указывает на место в исходном файле.

Команды: `sim validate`, `sim play <каталог> шаг.поле=значение …`,
`sim export-json <каталог>`.

## 6. Проверка сценария

CLI (`sim validate`), шаг сборки приложения и функция движка — одна
реализация.

1. Компиляция и схемы: фронтматтер, заголовки, блоки, параметры механик
2. Ссылки: переменные, ходы, шаги, условия, подстановки в тексте
3. Перебор путей: все комбинации ходов, влияющих на модель (`options` и
   `samples`). Если комбинаций слишком много — сэмплирование с покрытием
   каждого значения каждого хода хотя бы раз
4. На каждом пути — инварианты (п. 3.3) и параметры механик после
   подстановки
5. Бюджет времени: сумма `duration.max` шагов ≤ `duration_min`
6. Уроки сценария: выводы, подтверждённые условиями
7. Проверки сценария: эталонные прогоны и переборы

Отчёт — список сообщений формата
[scenario-format.md](scenario-format.md), п. 12: файл, строка, код, путь,
числа. Пригоден и для человека, и для обратной подачи в ИИ, если сценарий
писали с его помощью.

### 6.1 Эталонные числа принадлежат сценарию

Эталонные числа — в разделе `# checks` сценария, например канон v16 для
лимонада. Тест движка не содержит чисел ни одного сценария: он компилирует
все `scenarios/*`, прогоняет их проверки и уроки и падает, если хоть одна
не совпала.

Свои числа есть у учётного ядра и каждой механики: тесты на синтетических
данных, независимые от того, какие сценарии лежат в репозитории.

## 7. Версии

Сессия хранит копию скомпилированного сценария и мажорные версии механик,
с которыми он скомпилирован. Изменение поведения механики — новый мажор
(`funnel@2`), старый остаётся в библиотеке, пока на него ссылается хоть
одна незавершённая сессия.
