# Спека: соло-режим

> **Отложено.** Первая версия — только воркшоп с ведущим ([spec.md](../spec.md)).
> Документ сохранён как задел и не сверен с текущим форматом сценария.

Версия 2. Дополняет [spec.md](../spec.md). Всё, что относится к конкретному
сценарию — тексты разборов, точки «что было бы, если», итоговые показатели,
— задаётся в его `.md` ([scenario-format.md](../scenario-format.md)). Здесь —
только то, как соло-режим их исполняет.

---

## 1. Цель

Соло-режим — это воркшоп без ведущего и без зала. Один игрок проходит
сценарий в своём темпе, с сохранением.

Главная задача — довезти урок без разбора в диалоге. Вместо ведущего это
делают две вещи из сценария: **разбор** (слот `debrief`) после шага и
**таблица вариантов** (`variants`) — исход альтернативного решения рядом со
своим.

Три назначения, одна механика:

| Назначение | Кто играет | Чем отличается |
|---|---|---|
| Самостоятельный курс | сотрудник банка | вход без контакта |
| Лид-магнит | потенциальный клиент консалтинга | контакт, призыв в конце |
| Повторение после воркшопа | участник прошедшей сессии | сравнение с решениями его команды |

Различия задаются **профилем ссылки** (п. 7), а не сценарием и не отдельной
сборкой.

---

## 2. Прохождение и сохранение

Темп любой. Игрок может закрыть приложение на любом экране и вернуться.

**Что хранится.** Прогон: снимок сценария (spec.md, п. 7.2), seed, профиль
ссылки, решения. Состояние на любом шаге пересчитывается движком. Сохранение
— запись решения в базу после каждого ввода и номер текущего экрана.

**Кто игрок.**

- В Telegram — пользователь Telegram через `initData`. Вернулся в бота —
  продолжил с того же места.
- В вебе — анонимный токен устройства и ссылка «продолжить», которая
  восстанавливает прогон на другом устройстве.

Если в лид-профиле игрок оставил контакт, прогон привязывается к нему.

**Версия сценария фиксируется на старте.** Новое развёртывание с
изменённым сценарием не затрагивает незаконченный прогон: он доигрывается
по своему снимку.

---

## 3. Шаг в соло-режиме

Экраны шага и их порядок — из `screens` сценария. Соло-режим меняет только
правила по умолчанию:

- `discussion` пропускается, если у слота нет варианта `.solo`;
- `debrief` показывается в варианте `debrief.solo`, если он есть, иначе
  общий;
- ввод обязателен: экран `input` не пускает дальше без значения.
  Прогнозы и расчёты вводятся тоже, иначе урок «сначала назови своё число,
  потом посмотри» не работает;
- `teams` не показывается.

Кнопка называет действие по типу ввода: «Выбрать», «Дать прогноз»,
«Посчитать», «Дальше». Сценарий её не подписывает, поэтому противоречия
вроде «ход не нужен / сделайте ход» быть не может.

---

## 4. Разбор

Слот `debrief` шага. Показывается там, где его ставит `screens`, — по
умолчанию после факта и таблицы вариантов.

Требование к тексту: разбор объясняет механизм, а не пересказывает цифры —
цифры уже на экране факта. «Прибыль выше, денег меньше» — плохой разбор.
«Выручка признана в момент продажи, а деньги приходят, только когда
должник платит» — хороший.

Разбор пишется законченными мыслями, без опоры на голос ведущего. Если
ведущему нужен другой текст, у шага два варианта: `debrief.solo` и
`debrief.trainer`.

Разбор связан с уроком через раздел `# lessons`: если урок проверяет этот
шаг, валидатор при падении урока указывает и на разбор, который его
объясняет.

---

## 5. «Что было бы, если»

Экран `variants` шага. Игрок видит исход альтернативного решения рядом со
своим. **Свой путь не меняется** — переиграть можно только после финала
(п. 6). Смысл: увидеть цену своей ошибки, но прожить её до конца.

### Где показывается

На шаге, где раскрывается последствие, а не на шаге решения. Это задаёт
автор, ставя `variants` в нужный шаг; валидатор следит, чтобы решение было
не позже этого шага.

### Как считается

Движок перезапускает путь с теми же решениями и **тем же seed**, меняя
одно решение. Тот же seed обязателен: иначе в альтернативе выпадут другие
события, и разница будет не от решения, а от удачи.

### Что видит игрок

Для `choice` — все варианты, свой выделен. Для `number` — строки из
`values` сценария, собственный ввод игрока добавляется, если его там нет.
Колонки — из `columns`.

## 6. Переигровка и новая игра

После финала открывается переигровка **с любого решения**. Игрок выбирает
шаг; создаётся новый прогон: тот же снимок сценария, тот же seed, решения
до выбранного шага те же, дальше — свободно. Прогон привязан к исходному
через `parent_run`.

На финале переигровки — показатели `kpis` сценария рядом: «первый раз —
переигровка».

**Новая игра** — отдельно: новый seed, все решения свободны. Это и есть
реиграбельность, если в сценарии есть события.

| | Seed | Решения | Зачем |
|---|---|---|---|
| Переиграть решение | тот же | до выбранного шага те же | проверить «что если» до конца |
| Новая игра | новый | все свободны | другие события |

Новая игра всегда начинается на текущей версии сценария из каталога, а не
на снимке прошлого прогона.

## 7. Профили ссылки

Профиль — свойство ссылки, а не сценария. Один сценарий можно раздавать с
разными профилями.

```json
{
  "profile": "lead",
  "scenario": "<id из каталога>",
  "contact_gate": "before_final",
  "cta": { "text": "…", "url": "https://…" }
}
```

| Профиль | Контакт | Финал | Привязка |
|---|---|---|---|
| `internal` | не спрашиваем | итоги, переигровка | нет |
| `lead` | по `contact_gate` | итоги, призыв, переигровка | к контакту |
| `replay` | не спрашиваем | итоги + сравнение с командой на воркшопе | к сессии ведущего и команде |

`contact_gate`:

| Значение | Когда спрашиваем |
|---|---|
| `none` | никогда, только призыв в конце |
| `before_start` | до первого шага |
| `before_final` | перед итогами, после последнего шага |
| `before_replay` | при попытке переиграть |

По умолчанию для лидов — `before_final`: игрок уже вложил время, итоги —
самое ценное в прохождении.

**Повторение после воркшопа.** Ссылка выдаётся из сессии ведущего и несёт
идентификатор команды. Снимок сценария и seed берутся из сессии, иначе
сравнение некорректно. На финале рядом с показателями игрока — показатели и
решения его команды.

---

## 8. Финал

Экраны финала — из раздела `# final` сценария. Соло-режим добавляет то,
что зависит от профиля, а не от сценария:

- `kpis` в сравнении с первым прохождением или с командой (`replay`);
- экран `replay` — переигровка и новая игра;
- для `lead` — форма контакта по `contact_gate` и призыв из профиля.

В режиме ведущего финал — ретро в диалоге с залом. В соло его заменяют
разборы по ходу и таблицы вариантов: к финалу игрок уже видел цену каждого
своего решения.

## 9. Хранение и этапы

| Сущность | Поля |
|---|---|
| `run` | игрок, снимок сценария, хеш, seed, профиль, `parent_run`, текущий экран, статус |
| `decision` | прогон, шаг, ввод, значение, время |
| `link_profile` | профиль, сценарий, `contact_gate`, призыв, привязка к сессии |
| `contact` | прогон, контакт, согласие, время |

Дополнительные проверки валидатора для сценариев с `modes: [solo]`:

- у каждого шага с вводом есть `debrief` или `debrief.solo` (`W020`);
- у каждой таблицы вариантов решение не позже шага, где она стоит
  (`E045`);
- в финале есть `kpis`, если сценарий допускает переигровку.

| Шаг | Содержание | Готово, когда |
|---|---|---|
| M2.1 | Прохождение с сохранением, разборы, финал, профиль `internal` | оба сценария проходятся соло без правок кода |
| M2.2 | Таблицы вариантов в соло | |
| M2.3 | Переигровка и новая игра | |
| M2.4 | Профили `lead` и `replay` | |
| M2.5 | Telegram Mini App | один игрок проходит сценарий в Telegram |

## 10. Открытые вопросы

- **Согласие на обработку данных** в лид-профиле: текст, хранение,
  удаление. Нужна юридическая проверка до запуска.
- **Куда уходят лиды** — только в базу приложения или сразу в CRM и почту.
- **Разборы сценариев, написанных ИИ.** Валидатор проверяет, что разбор
  есть и привязан к уроку, но не качество текста. Ручная вычитка — на
  ревью pull request (spec.md, п. 12.1); достаточно ли этого?
- **Разделение прогонов** между внутренним курсом банка и консалтингом.

## Предложения — не входят в спеку до решения

**Прогноз перед разбором.** На ключевых шагах до разбора — вопрос с
вариантами: «Почему продажи выросли, а денег стало меньше?». Делается без
новых возможностей платформы: ввод `choice` без ссылок из механик и экран
`input` перед `debrief`.

**Оценка точности прогнозов.** Ввод `forecast` уже сохраняется. Можно
добавить ему поле `compare_to` — ссылку на фактическое значение — и на
финале показывать, насколько игрок ошибался.

**Персональная карта ловушек.** На финале отметить, в какие ловушки игрок
попал: для уроков `contrast` это вычисляется из его решений.

**Аналитика воронки для лид-профиля.** Где игроки бросают прохождение,
сколько доходят до контакта.
